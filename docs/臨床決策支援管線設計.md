## 0. 本文件的定位與整合方法

本文件整合五位子代理各自獨立設計的九階段管線（資料整合｜臨床趨勢｜併發症辨識｜風險計算｜Care Gap｜Guideline Recommendation｜醫師決策｜病人衛教｜後續追蹤）。五段設計是在互相看不到彼此程式碼的情況下平行完成的，因此存在下列三類落差，本文件逐一裁定並統一：

1. **命名不一致**：例如「資料整合」階段輸出的型別，第2/3段設計直接假設消費 `PatientEnrollmentState`，但第1段設計已把它包成更完整的 `PatientClinicalProfile`；「醫師決策」輸出的欄位名稱在第5段與第6段設計中互相不同（`disposition` vs `status`、`decision_date` vs `decided_at`）。
2. **重複實作同一件事**：HbA1c/LDL 良好/不良切點在「臨床趨勢」「風險計算」「Guideline Recommendation」三段設計中各自宣告了一份 `Config`，若不整併，未來三處數值可能各自被改動而不同步。
3. **資料契約假設未對齊**：後段設計（病人衛教/後續追蹤、Guideline/醫師決策）在看不到前段實際輸出型別的情況下，自行「猜」了一份上游資料形狀，與前段實際設計的型別不完全相同。

本文件的整合原則：**由「實際擁有該階段的設計」的型別做為準（canonical）**，下游若曾經自行假設一份形狀不同的替代型別，一律改為直接 import 上游實際型別（必要時上游型別新增 1-2 個欄位以滿足下游需求，並在文中註明是整合時新增的欄位）。所有裁定都在第 7 節「已解決的銜接落差」逐條列出、附裁定理由，方便日後回溯為什麼跟原始子設計不完全一樣。

**鐵律延續**（沿用五段設計已遵守的五條鐵律，整合時全部保留，未被放寬）：
1. 數值門檻只能來自 P14/P7 規格書明文，或明確標示為 illustrative placeholder 的可插拔風險模型。
2. 併發症碼表使用 ICD-10-CM 通用分類慣例，並在程式註解列出對照表。
3. 醫師決策階段只做決策支援紀錄，不做任何自動核准/自動下醫囑。
4. 病人衛教只設計「主題代碼→衛教資源」對照表架構，放 2-3 筆明確標示 placeholder 的範例，不生出正式衛教教材。
5. 所有無法回溯規格書的假設，一律用具名 Config 欄位 + TODO 註解顯式標示。

**資料流原則**（沿用 `models.py` 既有風格）：
- 每一站輸出一個獨立、盡量 `frozen` 的 dataclass 報告物件；**不**把所有欄位疊加進同一個越長越大的物件。
- `PatientClinicalProfile`（第1站輸出）是唯一被「每一站」都直接依賴的物件；其餘各站報告物件則是「鏈式」依賴（第 N 站的輸入 = profile + 第 2..N-1 站的報告物件），由管線編排層（見 8.6 節 `pipeline.py`）負責依序呼叫、把物件往下傳。
- 任何一站都不得回頭修改 `profile` 或更早期站的報告物件（唯讀輸入）。
- 任何「資料不足/依據不足」一律走顯式管道（`DataGapFlag` / `warnings` / `unregistered_codes` / `UNKNOWN` 列舉值）往下游傳遞，不得靜默假設。

## 3. (b) 各階段最終模組 / 函式 / 型別簽名

以下為**整合裁定後**的最終簽名（供實作工程師直接依此寫程式）。型別省略完整 docstring 內文，只保留欄位與整合相關的關鍵註解；完整規格依據見第 4 節彙整表。

### 3.0 共用型別列舉風格的整合裁定

五段設計中，「資料整合/臨床趨勢/併發症辨識」三段沿用 `dm_eligibility` 既有的「純字串常數」風格（如 `ClosureRecord.reason`），「風險計算/Guideline/醫師決策」三段改用 `class X(str, Enum)`。整合裁定：**Part 2（`dm_care_pipeline`）新增的所有「封閉受控詞彙」型別一律採用 `class X(str, Enum)`**（`TrendDirection`、`QualityMetricTier`、`RiskLevel`、`RecommendationPriority`、`EvidenceType`、`PhysicianDecisionStatus`），因為 `str, Enum` 既保有字串比較/序列化的相容性，又比裸字串多一層型別安全，較適合作為新套件的統一慣例；`dm_eligibility` 既有程式碼不受影響、不回頭修改。「併發症分類鍵」（`NEPHROPATHY` 等）與「照護碼字串」（`"P1407C"`）維持裸字串，因為它們本質是外部代碼表的 key，不是封閉的內部狀態機詞彙。

## 5. (d) 與既有 `src/dm_eligibility` 套件的關係

**原則：Part 2（`dm_care_pipeline`）只作為 `dm_eligibility` 的「使用者」（import），絕不修改 Part 1 任何既有檔案。**

1. **`PatientEnrollmentState` 與 `PatientClinicalProfile` 的關係是「composition，非繼承、非重新定義」**：`PatientClinicalProfile.enrollment_state: PatientEnrollmentState` 直接持有同一份物件參照。呼叫端（HIS 介接層）只需組裝一次 `PatientEnrollmentState`，同時餵給 `EligibilityEngine.evaluate()`（Part1）與 `build_patient_clinical_profile()`（Part2 第1站），兩邊互不干擾、互不複製資料。
2. **`EligibilityReport` 是「已收案狀態」的權威來源，Part2 不重新判斷收案資格**：第1站把它原樣收進 `profile.eligibility_report`；第5站 Care Gap 的 `codes_in_scope` 建議由呼叫端從它的 `eligible_codes()` 推導；第6站 Guideline / 第9站後續追蹤讀取它以避免「建議已收案病人重新收案」之類的重複動作。
3. **規則層（`rules_p14`/`rules_p7`）被直接重用、不重寫第二套判斷邏輯**：`LabRequirement` 常數表、`_with_ga_substitute()`、`check_lab_requirements()`、`check_stage2_entry_eligible()`、`check_quality_monitoring()`、`P7001_FIRST/SUBSEQUENT_INTERVAL_DAYS` 皆被 Part2 第2/5/9站直接 import 使用。這是**同一系統內模組間的刻意工程耦合**，不是誤用外部套件私有介面；若 `rules_p14.py`/`rules_p7.py` 未來修改這些函式簽名，Part2 對應模組會直接受影響，需同步調整。
4. **`EligibilityConfig` 被 Part2 多站直接重用**（Care Gap 用其 `allow_ga_as_hba1c_substitute` 確保替代規則一致；後續追蹤用其收案間隔設定），而非另建一份平行的設定物件——避免「Part1 認為 eligible，但 Part2 卻還顯示 gap」的不一致。
5. **`CKDAssessment.stage()` 是全系統唯一的 CKD 分期邏輯**，Part2 第3站 `ComplicationFinding.ckd_stage`、第4站 `RiskFactorSnapshot.ckd_stage` 皆直接重用同一方法的回傳值，不重新實作分期規則。
6. **建議的一項非破壞性重構**（不影響既有行為，僅供 `dm_eligibility` 維護者評估是否採納）：`rules_p14.py` 目前把品質監測 180 天四項內嵌在 `check_quality_monitoring()` 函式的區域變數中；若抽成模組層級具名常數 `QUALITY_MONITORING_LAB_REQUIREMENTS` 並 export，Part2 `care_gap.py` 便能直接 import 同一份定義，而非依賴函式回傳值反推。同樣地，`rules_p14.py` 內文寫死的 `70` 天字面常數，若比照 `rules_p7.py` 的 `P7001_SUBSEQUENT_INTERVAL_DAYS` 抽出為具名常數，`followup.py` 便不需要重申一份 `SUBSEQUENT_TRACKING_INTERVAL_DAYS=70`（目前是刻意重申以避免修改 Part1，屬技術債，已在 3.9 節註明）。

## 7. 已解決的銜接落差（五段設計整合時的裁定紀錄）

| # | 落差 | 原始設計分歧 | 本次裁定 | 理由 |
|---|---|---|---|---|
| 1 | 套件路徑 | `dm_careplan` vs `dm_care_pipeline` | `dm_care_pipeline` | 4/5段設計採用此名，多數裁定 |
| 2 | 第2/3站輸入型別 | 假設直接吃 `PatientEnrollmentState` | 改吃 `PatientClinicalProfile`（內部仍可經 `.enrollment_state` 取用原始物件） | 第1段設計已明確建議此簽名，且能順帶取得 `data_gaps`/`eligibility_report` 等第1站已算好的資訊，避免第2/3站重算 |
| 3 | HbA1c/LDL 切點宣告位置 | 三處各自宣告（trend/risk/guideline） | 收斂到 `trend_analysis.QualityThresholdConfig` 單一位置 | 避免未來修改切點時三處不同步；risk.py/guideline 一律消費 `MarkerTrend.control_tier` |

## 8. 仍待人工協調的事項（本文件無法單方面裁定，需相關團隊確認）

1. **HbA1C/LDL 良好/不良切點本身**（4.2節）：需臨床/品管端以健保署正式函釋核對數值與判定基準。
2. **風險計算公式**：`RuleBasedRiskCalculator` 是 illustrative placeholder，上線前需臨床端提供並驗證實際風險評分公式（如 ASCVD Risk Score、UKPDS Risk Engine），以新 `RiskCalculator` 實作替換。
3. **血壓資料來源**：`dm_eligibility/models.py` 目前無收縮壓/舒張壓資料結構（儘管 P14 spec 系統登錄必填欄位明文列出），`RiskFactorSnapshot.latest_systolic_bp/diastolic_bp` 目前恆為 `None`。需與「資料整合」實作者確認：擴充 `LabResult`（新增 vitals 用 item_code）或另建 `VitalSign` dataclass。
4. **eGFR/血壓的檢驗代碼**：`trend_analysis.py` 目前使用 placeholder 字串 `"EGFR"`/`"SBP"`/`"DBP"`，需與 HIS 介接確認實際資料來源。
5. **`CARE_GAP_REGISTRY` 缺漏代碼**（P1410C/P1411C/P4301C/P4302C/P4303C/P7003C）：需向健保署或院內系統文件補齊完整必要檢驗清單後才能註冊。
6. **Guideline 建議動作文字**（如「轉診眼科」）：非規格書明文之臨床處置要求，需臨床端逐條審閱 `action_is_placeholder_content=True` 的規則。
7. **病人衛教對照表內容**：`complication_to_topics`/`resources_by_topic` 目前僅 2-3 筆 placeholder，需衛教/個管團隊提供正式教材。
8. **後續追蹤監測間隔**：足部檢查/CKD複評間隔為工程佔位值，需依實際採用之照護指引（ADA/台灣糖尿病學會）訂定。
9. **`rules_p14.py` 兩項非破壞性重構建議**（5.6節）：品質監測180天四項抽成具名常數、70天間隔抽成具名常數，供 Part2 直接 import，避免技術債累積；是否採納由 `dm_eligibility` 維護者決定。
